更好服务的AI

2026-09-02 00:00 · Exploration

00-现情

人工智能技术的不断发展，使得各种大模型已经开始改变日常的生活。在代码自动化编辑与智能体辅助开发中，这点尤甚。但是如果想要拥有较好的开发效果，单纯的提问提示效率可能较为低下，效果也不尽人意。

从使用经验来说，如果是工程开发或者是项目研究，基于 git 进行管理可能不失为一种较好的选择。git 的错误回退、变更前基于 diff 的二次改动确认等都非常有利于开发结果的稳定性和可用性。

01-Structure

目前常用且觉得有利的初始项目结构为：

<项目根>/
	README.md # 项目入口
	AGENTS.md # Agent 行为约定
	CONTRIBUTING.md # 贡献指南
	TODO.md # 任务总线
	CHANGELOG.md # 变更日志
	LICENSE # （可选）开源协议
	SECURITY.md # （可选）安全漏洞报告渠道与安全约定
	.gitignore # 忽略规则
	.gitattributes # 换行符归一化
	.editorconfig # （可选）缩进/编码/行尾统一
	.env.example # （可选）环境变量
	.agents/ # 项目级 Agent 资源
		skills/ # 项目专属 skills
			git-commit/SKILL.md # 提交约束
			development/SKILL.md # 开发约束
			project-init/SKILL.md # 项目初始化
		mcp.json # 项目级 MCP 配置
	docs/
		DESIGN.md # 设计文档
		DEVELOPMENT.md # 实现文档
		RESEARCH.md # （可选）研究结论沉淀
		GLOSSARY.md # （可选）术语表
		template/ # 模板库
			issue.md # issue 模板
			PR.md # PR 模板
			decision.md # 决策（ADR）模板
		decisions/ # 重要决策记录（ADR）
			0001-<标题>.md # 每个决策一个文件
	src/ # 开发代码空间
	tests/ # 测试
	scripts/ # 项目脚本
	reference/ # 参考文档
	source/ # 参考源文件/大工具
	examples/ # （可选）示例/演示代码

对于小型个人开发项目也可以精简为：

<项目根>/
	README.md # 项目入口
	AGENTS.md # Agent 行为约定
	TODO.md # 任务总线
	CHANGELOG.md # 变更日志
	.gitignore # 忽略规则
	.agents/ # 项目级 Agent 资源
		skills/ # 项目专属 skills
			git-commit/SKILL.md # 提交约束
			development/SKILL.md # 开发约束
	docs/
		DESIGN.md # 设计文档
		DEVELOPMENT.md # 实现文档
	src/ # 开发代码空间
	reference/ # 参考文档
	source/ # 参考源文件/大工具

NOTE

source/ 与 reference/ 的区分：前者是第三方源码、大体积工具，只作参考、不入库；后者是值得入库存档的文档。

如果不需要其他人协同，一些 PR 等的模板和 CONTRIBUTING.md 文档便不再需要了。

02-agents/skills

系统级或者项目级至少需要两个skills，一个管「怎么提交」，一个管「怎么开发」：

一个服务于git，约束 git 提交的时机、提交的要求、提交的条件；一个服务于developemnt，约束开发有关的行为，包括但不限于开发前读取约束文档、开发时最小化改动、开发后测试、测试后同步文档并且在难以抉择部分申请人工审核协助。例如：

---
name: git-commit
description: 本项目的 git 提交约束。任何提交（commit）、暂存、分支操作前使用，约束提交时机、提交要求与提交条件。
---

# Git 提交约束（项目级）

## 何时使用

- 任何 `git commit` / `git add` / `git push` / 分支操作之前
- 完成一个可验证的开发增量之后
- 变更涉及文档、配置、结构时

## 一、提交时机（什么时候该提交）

1. **每个完成且验证通过的增量提交一次**：实现切片 → 测试通过 → 立即提交 → 进入下一个切片。
2. **不可攒大 commit**：未提交的改动不允许堆积超过「一个逻辑变更」。
3. **中途停止必提交**：会话中断、切分支、下班前，把当前已完成且验证的部分提交掉，保证随时可回退到已知良好状态。
4. **文档变更、配置变更独立提交**，不混入代码变更。

## 二、提交条件（满足全部才能提交）

1. 类型检查/构建/测试全部通过（以 `DEVELOPMENT.md` 中记录的验证命令为准）。
2. `git diff` 复查确认：无多余文件、无构建产物、无缓存、无 `.env` 等敏感内容。
3. 涉及用户可见行为 → `docs/CHANGELOG.md` 已追加条目。
4. 涉及设计/实现/规则 → 对应文档已同步（`DESIGN.md` / `DEVELOPMENT.md` / `AGENTS.md`）。
5. 变更已完成，无半成品（进行中的工作用 `🚧` 标记单独提交，禁止和成品混在一起）。

## 三、提交要求（格式规范）

采用 **Gitmoji 图标 + Conventional Commits**：

```
<icon> <type>(<scope>): <subject>

<body>（可选）

```

- **subject**：动宾结构开头（新增/修复/优化/移除…），≤ 50 字符，不以句号结尾；超长说明该拆分。
- **body**（复杂变更必写）：按「为什么 → 怎么改 → 影响面」三部分组织。
- **type 与图标**（沿用 Gitmoji 标准，不自创）：

| type | 图标 | 含义 |
| --- | --- | --- |
| feat | ✨ | 新功能/新页面/新字段 |
| fix | 🐛 | 修复 bug |
| style | 🎨 | 样式/视觉调整，不改行为 |
| refactor | ♻️ | 重构，行为不变 |
| perf | ⚡️ | 性能优化 |
| docs | 📝 | 文档变更 |
| chore | 🔧 | 依赖/构建流程/配置 |
| build | 🚀 | 构建/发布/管线 |
| test | ✅ | 新增或修改测试 |
| revert | ⏪️ | 回滚 |

补充：🎉 项目初始化；🔥 删除代码；⬆️ / ➕ / ➖ 升级/新增/移除依赖；🚧 开发中。

## 四、提交流程

1. 跑验证命令（类型检查/构建/测试）
2. `git status` + `git diff` 检查改动范围
3. 拆分：一个 commit 只做一件事，无关改动分次 `git add <path>`
4. 对照文档同步规则，确认变更已记录
5. 按格式提交；提交后 `git log -1 --stat` 复查内容完整

## 五、红线（禁止）

- 不提交 `.env`、密钥、构建产物（`dist/`、`.next/`、缓存）、`source/` 目录
- 格式化/重构与行为变更不混在同一个 commit
- 不 force push 共享分支；push 前确认目标仓库公开性
- 历史重写（reset/rebase/filter-*）前先备份并征求确认
- 提交信息禁用 "update"、"fix"、"misc" 等无信息量措辞

## 核对清单

- [ ] 类型检查/构建/测试通过
- [ ] diff 无多余文件、无敏感内容
- [ ] 图标与 type 对应正确，subject 动宾、≤50 字符
- [ ] 一个 commit 只做一件事
- [ ] 文档/CHANGELOG 已同步
- [ ] `git log -1 --stat` 复查通过
---
name: development
description: 本项目的开发约束。任何代码/文档/配置变更前使用：开发前读取约束文档、开发时最小化改动、开发后验证测试、测试后同步文档、难以抉择时申请人工审核。
---

# 开发约束（项目级）

## 何时使用

- 开始任何代码变更（新功能、修 bug、重构、样式、配置）之前
- 变更涉及文档、目录结构、依赖时

## 一、开发前：先读约束，再动手

1. 阅读根目录 `AGENTS.md` 与 `README.md`，掌握项目约定、命令、目录职责。
2. 阅读 `docs/DESIGN.md`（设计意图）与 `docs/DEVELOPMENT.md`（实现/构建/验证方式）。
3. 从 `TODO.md` 或 issue 领取任务；修改不熟悉的文件前先 `Read` 目标文件。
4. 明确「本次变更目标与验收标准」，无关事项记入 TODO，不顺手做。

## 二、开发中：最小改动

1. 只改达成目标所需的文件与代码；不做顺手重构、不格式化无关区域。
2. 一个变更只做一件事；三个相似行好过提前抽象。
3. 新代码风格对齐周边代码（命名、注释密度、结构习惯）；复用项目已有工具函数与组件。
4. 不引入未经确认的新依赖；确需新增时评估体积与必要性并记录。
5. 不删除自己不理解的东西；删除代码前先确认用途。

## 三、开发后：验证与测试

1. 任何变更后至少跑静态/类型检查；涉及构建跑构建，涉及逻辑跑测试（命令见 `DEVELOPMENT.md`）。
2. 涉及浏览器/交互的变更做运行时验证。
3. 完成后复查 diff：确认改动最小、无多余文件。

## 四、测试后：同步文档（强制）

1. 改动设计/结构/API → 更新 `docs/DESIGN.md`
2. 改动实现/构建/配置/命令 → 更新 `docs/DEVELOPMENT.md`
3. 任何用户可见变更 → `docs/CHANGELOG.md` 追加一条（日期 + 内容 + 影响面）
4. 变更了仓库规则 → 同步更新 `AGENTS.md` 相关条目
5. 重要决策（有取舍、有替代方案被否决）→ 在 `docs/decisions/` 新建 ADR 记录
6. 删除文档与代码中过时的旧描述

## 五、难以抉择时：申请人工审核

遇到以下情况**必须暂停并列出选项与利弊，请用户/维护者决策**，不得自行拍板：

1. 需求相互矛盾或与现有代码行为冲突
2. 方案存在明显取舍（性能 vs 简洁、兼容 vs 迁移成本等）
3. 变更影响面超出原定目标（结构重组、接口变更、行为语义变化）
4. 删除文件、覆盖未提交变更、清理缓存等不可逆操作
5. 新依赖、新目录、对外接口的引入

## 六、安全红线

- 敏感内容（密钥、密码、隐私数据）绝不入库，且历史中无残留
- 读写/安装/删除操作保持在工作目录内；确需外出先确认
- 不擅自安装系统级工具；优先项目/隔离环境已有能力
- `.env`、密钥文件只走受控工具读取，不经 shell 命令复制/传输

## 核对清单

- [ ] 已读 AGENTS.md / DESIGN.md / DEVELOPMENT.md / TODO.md
- [ ] 改动最小化，无顺手重构、无多余文件
- [ ] 新代码风格对齐周边，无未经确认的新依赖
- [ ] 类型检查/构建/测试通过
- [ ] 设计/实现/配置文档已同步，CHANGELOG 已追加
- [ ] 重要决策已记 ADR
- [ ] 难以抉择/破坏性操作已确认
- [ ] 无敏感内容入库

03-agents/mcp

WARNING

需要注意的是，绝大部分 mcp 都会使得智能体超出其所有的权限，需要也应当对其进行的一些关键设施操作保持谨慎态度！

项目级 MCP 的配置，按需接入。过多的无用冗余 MCP 会占用上下文与连接成本，按类型的参考：

场景 推荐 MCP 用途
浏览器/前端 Playwright/Chrome DevTools MCP 交互验证、端到端测试
通用工具 filesystem / sequential-thinking 文件操作 / 复杂多步推理
数据项目 sqlite / postgres / mysql 查库、调试
研究类 fetch / web search 相关 抓取、检索参考资料
安全审计 mimosa 项目安全扫描
文档生成 document-skills（docx/pdf/pptx） 出文档产物
逆向分析 ida-pro-mcp 连接IDA pro工具

同时建议将 mcp 的使用方式记录为 skills 或者记录在 DEVELOPMENT.md 文档中。

NOTE

如果是在 vsocde中进行开发，部分 mcp 会通过 vscode 代理来提供给内部的智能体，这个时候可能会出现工具暴漏不完全的情况，比如 ida-pro-mcp 只暴漏三个工具。可以将此问题交给智能体自己，让其在 skills 目录下同步生成一个使用此 mcp 且绕过 vscode 代理的方法。

04-AGENTS.md

这是目前主流 AGENT 都会自动读取的项目规则文件（同时，如 claude 读取的是 CLAUDE.md，需要进行链接或者其他适当操作），参考模板如下：

# <项目名> — Agent 工作约定

## 项目简介
<一句话说明项目是什么、解决什么问题>

## 仓库导航
- `src/` 开发代码
- `docs/DESIGN.md` 设计意图（改结构/接口前先读）
- `docs/DEVELOPMENT.md` 实现细节、构建与验证命令（动手前先读）
- `docs/CHANGELOG.md` 变更日志（用户可见变更必更新）
- `docs/decisions/` 重要决策记录（ADR）
- `reference/` 参考文档 | `source/` 参考源文件（不入库）
- `TODO.md` 任务清单（领取/登记任务在此）

## 工作流（必须遵守）
1. 任何变更前，调用 `development` skill：先读上述文档，理解再动手
2. 最小改动：只改目标所需，不顺手重构、不添加投机性抽象
3. 验证：变更后运行 `DEVELOPMENT.md` 记录的检查/构建/测试命令
4. 同步文档：设计→DESIGN.md，实现→DEVELOPMENT.md，用户可见→CHANGELOG.md，取舍决策→decisions/
5. 提交按 `git-commit` skill：Gitmoji + Conventional Commits，一个 commit 一件事
6. 难以抉择/破坏性操作：暂停并征求维护者确认，不自行拍板

## 约定速览
- 提交格式：`<icon> <type>(<scope>): <subject>`，subject 动宾、≤50 字符
- 语言：提交与文档用 <中文/英文>，代码标识符用 <英文>
- 敏感信息（密钥、.env、隐私）绝不入库；`source/` 目录不入库

## 常用命令
- 开发：`<npm run dev / ...>`
- 验证：`<npm run check / build / test>`

## 红线
- 不 force push 共享分支；不提交 .env/构建产物
- 不删除不了解的代码；破坏性操作先确认
- 遇到矛盾需求或歧义，停下来提问，不猜着做

05-其他可能有用的行为

TODO.md 作为任务总线使用：从 TODO 领取任务、完成勾选、放弃说明、更新迭代等。

ADR 决策记录：有取舍方案的决定，写一条 docs/decisions/，防止后期迂回工作。

把研究结论进行沉淀：reference/ 只存素材且可能是很多的和临时的，结论应要落到 docs/RESEARCH.md 或 ADR。

变更摘要：每次改动后按「改了什么 / 特意没动什么 / 潜在问题」三段式汇报，方便 review 和排查。
